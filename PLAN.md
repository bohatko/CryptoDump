# CryptoDump — сканер откупов после дампа на фьючерсах OKX

Статус: M0 готов, сканер работает на живом потоке; из M4 сделаны веб-дашборд и история в
SQLite. Дата: 2026-10-29.
Карта кода и правила изменений — [AGENTS.md](AGENTS.md).

## 1. Цель

Ловить момент **откупа после резкой просадки** на деривативах OKX и присылать алерт,
в котором уже есть всё для быстрого решения: инструмент, окно просадки, процент, цена,
состояние стакана и поток агрессора (CVD).

Задача не «предсказать дно», а **отфильтровать шум**: дамп + живой стакан + признаки
того, что продавца выкупают. Поэтому алерт формируется только когда сработало окно
просадки **и** стакан проходит фильтр ликвидности **и** набрался минимум сигнатур откупа.

## 2. Что берём с OKX

### 2.1 Public WebSocket

> Проверено на живом API: порт **8443 выводится из эксплуатации** (OKX присылает
> `notice 64010`), поэтому используется `wss://ws.okx.com:443`. Свечи живут на
> **отдельном `business`-эндпоинте** — на `/ws/v5/public` подписка на `candle1m`
> возвращает ошибку `60018 channel doesn't exist`. Подписки раскладываются по
> эндпоинтам автоматически (`okx_ws.split_by_endpoint`).

| Канал | Эндпоинт | Зачем | Нюанс |
|---|---|---|---|
| `books` | `/ws/v5/public` | **основной источник стакана**: snapshot 400 уровней + инкременты ~100 мс | проверено: работает **без логина**; `checksum` всегда `0`, целостность — по `seqId`/`prevSeqId` |
| `trades` | `/ws/v5/public` | реальные сделки: `px`, `sz`, `side` (сторона **тейкера**) | источник и для CVD, и для точного максимума окон |
| `candle1m` | `/ws/v5/business` | минутные свечи (в т.ч. незакрытая, `confirm=0`) | база для окон 30m/1h/2h |
| `books5` | `/ws/v5/public` | быстрый top-of-book, 5 уровней | не используется: 5 уровней не проходят фильтр на 20 |
| `liquidation-orders` | `/ws/v5/public` | ликвидации по `instType` | публикуется только для SWAP, приходит пачками |
| `tickers` | `/ws/v5/public` | опционально: last / 24h | в скелете не подписываем, цена берётся из сделок |

### 2.2 REST (`https://www.okx.com`)

| Метод | Зачем |
|---|---|
| `GET /api/v5/public/instruments?instType=SWAP\|FUTURES` | вселенную инструментов собираем из REST, а не хардкодом; здесь же **`ctVal`** — размер контракта |
| `GET /api/v5/market/tickers?instType=...` | ранжирование по 24h обороту, чтобы взять top-N |
| `GET /api/v5/market/books?instId=...&sz=20` | резервный источник стакана (`depth.source: "rest"`); в штатном режиме стакан идёт из WS `books` |
| `GET /api/v5/market/candles?bar=1m&limit=125` | бутстрап истории окон на старте (иначе первые 2 часа окна 2h пустые) |

### 2.3 Про «сырьё» и квартальные

- OKX торгует **крипто-деривативами**: `SWAP` (перпетуалы) и `FUTURES`
  с экспирациями `this_week` / `next_week` / `quarter` / `next_quarter`.
- Товарных фьючерсов (нефть, золото, газ) у OKX **нет**. Если нужен именно товарный рынок —
  это другой источник, но конфиг (`market.inst_types`, `market.quote_ccy`, `market.symbols`)
  специально сделан расширяемым: добавление второго коннектора не потребует переписывать ядро.
- Квартальные фьючерсы берём тем же кодом: они приходят из `instType=FUTURES`
  (`instId` вида `BTC-USDT-260327`), поток и метрики идентичны свопам.

### 2.4 Ограничения, которые надо держать в голове

- `/market/books` — порядка 40 запросов / 2 c на IP, поэтому REST-поллинг годится только
  как резерв на короткой вселенной; штатно стакан идёт из WS `books` (без логина).
- `books` дорогой по трафику (~28 МБ/час на инструмент) — см. §5.5, почему он подключается
  по требованию.
- Лимит подписок на соединение и на IP ограничен; при большом списке — несколько соединений
  и/или фильтр по обороту.
- **480 запросов `subscribe`/`unsubscribe`/`login` в час на соединение.** Сверх — ошибка
  `60014 Requests too frequent`, а после затяжного шторма OKX перестаёт слать данные по
  соединению, хотя оно «подключено» (наблюдали: сделки по 455 инструментам замолчали,
  сканер ослеп). Повторный `subscribe` уже подписанного `books` нового snapshot не даёт,
  поэтому ресинк стакана — это пара `unsubscribe` + `subscribe`. Как это учтено — §5.5.
- Данные с OKX — не биржевой тик-бай-тик: у public-каналов есть агрегация и задержка.
  Реакция в 100–500 ms — норма, «мгновенно» не будет.
- `liquidation-orders` неполный: это не все ликвидации рынка, а то, что биржа публикует.
  Поэтому затухание ликвидаций — **подтверждающий** сигнал, а не основной.

## 3. Архитектура

```
            REST bootstrap (universe.py: instruments + ctVal, tickers, candles)
                                   │
    ┌──────────────────────────────┴───────────────────────────────────┐
    │                         Engine (оркестратор)                      │
    │                                                                   │
    │  OkxPublicStream ×2 ──► WsRouter ──► InstrumentState              │
    │   public: trades,          (канал →    ├─ OrderBook               │
    │     books*, liquidations    обработчик) ├─ CandleBook              │
    │   business: candle1m                    ├─ TradeWindow (CVD, high) │
    │   (reconnect, ping,                     ├─ DropWindows             │
    │    subscribe на лету)                   └─ LiquidationTracker      │
    │          ▲      ▲                                                 │
    │          │      └── DepthGuard: разрыв seqId / протух → resubscribe│
    │          └───────── DepthScheduler: слоты books под дампы (TTL)   │
    │                           ▲                                       │
    │  eval (каждые 2 c):       │ DropSeen (просадка, стакана нет)      │
    │    evaluate_instrument() ─┴─► Alert ─► AlertRouter (кулдаун)      │
    └───────────────────────────────────────────┼───────────────────────┘
                                                ▼
                              console · JSONL · webhook · Telegram
```

Ключевая идея: **всё состояние по инструменту лежит в одном объекте** (`InstrumentState`),
а оценка (`evaluate_instrument`) и детекторы — чистые функции над снимком этого состояния.
Это позволяет позже прогнать тот же код по записанным сообщениям (replay) без сети.
`*` — `books` подписан не на всех: см. §5.5.

## 5. Расчёты

### 5.1 Окна просадки

Окна: `1m`, `5m`, `30m`, `1h`, `2h` (список и пороги — в конфиге, меняются на лету).

**Два источника максимума** (важно для точности):

- **1m и 5m — по сделкам** (`TradeWindow`, секундные бакеты). Раньше high брался из
  1m-свечей, пересекающих границу окна (`end_ts > start`), из-за чего в окно 1m попадал
  максимум почти за 2 минуты, а в 5m — почти за 6. Это завышало просадку и давало
  ложные срабатывания. Точность по сделкам — до секунды.
- **30m/1h/2h — по 1m-свечам** (`CandleBook`): минута погрешности на получасовом окне
  это 0.8%, а память под 7200 бакетов на инструмент тратится зря.

Порог переключения — `cvd.precise_windows_until_s` (300 с). Если по трейдам данных ещё
нет (инструмент только что добавлен), короткое окно честно считается по свечам: грубая
оценка лучше пропуска дампа.

- `drop_pct = (price / high - 1) * 100`, где `price` — последняя сделка (если свежее 30 c), иначе закрытие свечи.
- Срабатывание: `-drop_pct >= порог_окна`, пороги задаются положительными числами
  (например `{"1m": 1.5, "2h": 12}` = просадка 1.5 % и 12 %).

Почему от `high`, а не от `open`: нам важен масштаб движения, а не форма свечи.

### 5.2 Стакан и фильтр ликвидности

**Критично:** OKX отдаёт размеры (`sz`) в **контрактах**, а не в монетах. Один контракт
`BTC-USDT-SWAP` = 0.01 BTC, `ETH-USDT-SWAP` = 0.1 ETH и т.д. Поэтому любая сумма
считается как `px * sz_contracts * ctVal`, где `ctVal` берётся из `/public/instruments`.
Без этого фильтр «1 млн USDT» ошибается в десятки-сотни раз на разных инструментах.

- `notional(level) = px * sz * ctVal` в USDT; суммируем top-20 уровней с каждой стороны.
- Фильтр: `bid_notional + ask_notional >= depth.min_notional_usdt` (по умолчанию **1 000 000 USDT**).
  Дополнительно можно потребовать минимум по одной стороне — задел на M3.
- `require_full_depth`: сумма считается только по полному снимку на 20 уровней.
- **Свежесть в инкрементальном режиме считается по стакану, а не по уровню.**
  В канале `books` биржа присылает только изменившиеся уровни: стоящая стена без
  изменения объёма не попадает в апдейты, её `ts` не обновляется. Фильтр по
  `stale_level_s` выбрасывал бы ровно ту стену, которую мы ищем, причём точно на
  пороге `wall_persist_s` (оба по умолчанию 10 с). Поэтому живость определяется
  временем последнего апдейта стакана (`stale_after_s`), а уровни не отбрасываются.
  Фильтр по `level.ts` остаётся только для режимов, где у уровней есть собственное
  время (`per_level_ts`).
- **Глубина хранения больше расчётной.** Стакан хранит до `depth.store_levels` (100)
  уровней из WS-снимка, а срез до `depth.levels` (20) делается в `summary()`.
  Иначе при выедании верхних уровней снизу нечего подтянуть и глубина временно
  падала бы ниже 20.
- **Ресинк — переподпиской, не REST.** Канал `books` на `subscribe` отдаёт полный
  snapshot с актуальным `seqId`, поэтому при разрыве цепочки канал переподписывается
  (проверено на живом API). Накладывать REST-снимок на WS-инкременты нельзя: у них
  разные точки отсчёта, и первый же апдейт дал бы расхождение с биржей. REST-поллинг
  работает только при `depth.source == "rest"`. Переподписка одного инструмента
  ограничена кулдауном (`max(5 c, poll_interval_s)`), чтобы неудачный ресинк не
  превратился в шторм запросов.
- Источник по умолчанию: **канал `books`** (`depth.source: "ws"`), возраст стакана
  ~40–100 мс на живых замерах.
- Имбаланс: `bid_notional / ask_notional`.
- **Стена на бидах**. Две поправки, без которых сигнатура бесполезна (проверено на живых
  данных OKX):
  1. Лучший бид стеной не считается (`wall_exclude_top_level`): у `BTC-USDT-SWAP` верхний
     уровень держит ~96% объёма top-20, поэтому «стена» находилась в каждом снимке.
  2. База сравнения — **среднее** по уровням ниже лучшего бида, а не медиана: у BTC
     половина уровней это пыль по 16–500 USDT, медиана даёт ratio в тысячи раз
     (наблюдалось 6535×), а по среднему — 2–15×, и порог 4× осмыслен.
- Условия стены: `notional >= wall_multiplier × среднее` и
  `notional >= wall_min_notional_usdt` (по умолчанию 4× и ≥ 300k USDT).
- Устойчивость: стена считается настоящей, только если простояла `wall_persist_s` (10 c)
  на той же цене (±0.2%) с номиналом ±35%. Меряем временем, а не числом снимков: WS даёт
  ~10 снимков в секунду, и «3 снимка» спуф проходит за 300 мс. Мигающий спуф отсекается.

### 5.3 CVD / поток агрессора

- По каналу `trades`: `notional = px * sz * ctVal` (sz в контрактах),
  `signed = +notional` для `side="buy"` (тейкер покупает), `-notional` для `sell`.
- `CVD(w) = Σ signed` за окно `w` (5 минут по умолчанию).
- Две сигнатуры откупа:
  1. **Разворот**: окно делим на три части; `sum(последняя треть) > 0` и
     `sum(последняя) >= cvd_reversal_ratio * |sum(первые две)|` (по умолчанию 0.6) —
     то есть покупатель откупил заметную долю того, что продали.
  2. **Всплеск тейкеров**: `buy_notional / sell_notional > cvd_taker_buy_ratio` (1.35) за
     последние `cvd_burst_s` (60 c).

### 5.4 Затухание ликвидаций

- По `liquidation-orders`: суммируем `bkPx * sz * ctVal` (sz тоже в контрактах).
- Окно `liq_decay_window_s` (5 мин) делим на «раньше» (2/3) и «сейчас» (1/3), считаем **темп** (USDT/с).
- Сигнатура: `rate_now < liq_decay_ratio * rate_earlier` (0.35) при
  `earlier_notional >= liq_min_notional_usdt` (200k).
  Смысл: каскад ликвидаций был и **выдохся** — давление продавца кончилось.

### 5.5 Покрытие рынка и стоимость данных

Замерено на живом API (511 USDT-перпетуалов OKX):

| Канал | Стоимость | Вывод |
|---|---|---|
| `trades` × 511 | 397 сообщ/с, **309 МБ/час** | можно слушать весь рынок на одном соединении |
| `books5` × 1 | **4.8 МБ/час** | дёшево, но всего 5 уровней |
| `books` × 1 | **28 МБ/час** | на 511 инструментах это 13 ГБ/час — недопустимо |

Поэтому используется **трёхуровневая схема**:

1. `trades` + `candle1m` — на все инструменты с оборотом ≥ `market.min_turnover_usdt`
   (по умолчанию 100k/24ч: отсекает ~67 мёртвых из 511, где 6–20k в сутки).
   Так просадка и CVD считаются по **всему рынку**.
2. Дамп найден → `DepthScheduler` выделяет слот и подписывает `books`
   (`depth.mode: "ondemand"`, `book_slots: 20`, `book_ttl_s: 180`).
3. Стакан живёт 3 минуты после последнего срабатывания, затем отписывается;
   при переполнении вытесняется инструмент с самой слабой просадкой.

Итоговый трафик: ~300 МБ/час (трейды) + до 20 × 28 = 560 МБ/час (стаканы) ≈ 0.9 ГБ/час.
Против 13 ГБ/час, если держать стакан на всём рынке.

Цифры плавают с активностью рынка: повторный замер `tools/channel_cost.py` (20 c, спокойный
рынок) дал `trades` × 511 — 120 МБ/час, `books` на BTC/ETH — 55 МБ/час на инструмент.
Порядок и вывод те же: `books` на весь рынок — десятки ГБ/час. Перемерить:
`python tools/channel_cost.py --seconds 60`.

Режимы `depth.mode`:

- `"ondemand"` (по умолчанию) — стакан под дампы, максимум покрытия;
- `"top"` — стакан сразу для `book_slots` инструментов с наибольшим оборотом;
- `"all"` — стакан на всё (имеет смысл только на маленькой вселенной).

Сторож стакана (`DepthGuard`) чинит разрывы `seqId` только у стаканов, которыми кто-то
владеет: статические из `top` и слоты планировщика старше 5 c (`BOOK_GRACE_S` — время на
первый snapshot). Смена `depth.mode`/`depth.source` на лету не применяется — нужен рестарт.

Бюджет запросов подписки (лимит 480/ч, §2.4) держат три уровня:

- **`OkxPublicStream`** хранит желаемый набор подписок и то, что уже отправлено на текущем
  соединении. Раз в 0.4 c `flush` отправляет **один** запрос с разницей (сначала
  отписки, потом подписки, пачкой до `chunk_size`), не больше `OPS_PER_HOUR = 400` в час.
  Подписка и отписка до отправки взаимно гасятся. На `60014` — пауза 5 → 60 c и повтор
  того же запроса (по `id`); на прочие ошибки (инструмент снят) повтора нет до реконнекта.
  Сторож потока: канал с ≥ 20 подписками молчит > 60 c → реконнект.
- **`DepthGuard`** — экспоненциальный backoff ресинка на инструмент: 5, 10, 20 … 120 c;
  счётчик сбрасывается, когда стакан 60 c здоров.
- **`DepthScheduler`** — слот нельзя вытеснить раньше `book_min_hold_s` (30 c), а
  отпущенный инструмент не получает слот `book_retry_s` (10 мин), если его просадка не
  углубилась в 1.5 раза. Иначе две соседние просадки менялись слотами каждый тик.
  Слот продлевается и когда стакан есть, но score не добран (`STATUS_LOW_SCORE`).

Расход виден в шапке дашборда (`WS запросов/ч`) и в `/api/status` → `streams[].budget`.

#### Фильтр ликвидности

Порог `depth.min_notional_usdt = 1 000 000` на 20 уровнях пропускают **15 из 511**
инструментов (2.9%): SOL, XAG, KORU, DOGE, BTC, ETH, TRUMP, XRP, CL, XAU, SNDK, ADA,
SOXL, SPCX, SKHYNIX. Это осознанное решение: фильтр отсекает 97% рынка, поэтому
детекция просадки от него не зависит — он проверяется **после** того, как дамп уже
найден, и только на инструментах с подключённым стаканом.

Повторный замер `tools/liquidity_probe.py --rounds 2` — 19 из 511 стабильно проходят
(к списку выше добавились PUMP, LTC, DRAM, NEAR), «мигающих» нет. Список зависит от рынка,
перепроверять перед правкой порога.

## 6. Скоринг алерта

Алерт отправляется, если:

```
просадка >= порог окна
И стакан свежий И total_notional(top20) >= 1 000 000 USDT
И количество сработавших сигнатур >= signals.min_score (по умолчанию 2 из 3)
```

Каждая сигнатура даёт 1 балл; при желании веса выносятся в конфиг (M3).

Дедуп: кулдаун `alerts.cooldown_s` (5 мин) на пару `(инструмент, окно)`, чтобы не спамить
пока цена висит на дне. Кулдаун сбрасывается, если просадка углубилась ещё на 1 п.п. (TODO M2).

## 7. Конфиг

`scanner/config.example.json` + горячая перезагрузка: `engine` раз в `reload_interval_s`
сверяет mtime файла; пороги окон, фильтры стакана и сигналы применяются без рестарта.
Смена `market.*` (вселенная, URL) требует рестарта — в лог пишется предупреждение.

Секреты в конфиг не попадают: `alerts.telegram` хранит только **имена** переменных
окружения (`token_env`, `chat_id_env`), а значения читаются из `.env`/окружения процесса.
`.env` в `.gitignore`, шаблон — `.env.example`.

### Персист состояния

`engine.persist_state` (по умолчанию включён) сохраняет в `state.json` секундные бакеты
трейдов, события ликвидаций и отметки кулдауна. Без этого после рестарта `cvd_fade` и
`liq_decay` молчат, пока не наберётся 5-минутное окно, а кулдаун обнуляется и может
продублировать только что отправленный алерт.

- бакеты хранятся только за `max(precise_windows_until_s, cvd.window_s × 2, 600)` секунд
  (≈10 мин), а не все 2 часа: длинные окна считаются по свечам, и в файл не уезжают
  лишние 7000 бакетов на инструмент;
- запись атомарная: уникальный `.tmp` → `os.replace` с ретраями, плюс лок, потому что
  фоновый цикл и финальное сохранение могут идти одновременно (на Windows это давало
  `Permission denied`);
- снимок старше `state_max_age_s` (15 мин) не восстанавливается: протухшие бакеты
  только запутают детекцию;
- состояние из будущего (сменили часы) тоже игнорируется.

## 8. Формат алерта

Алерт — это готовый план лонга (`scanner/plan.py`, секция конфига `trade`), а не набор
метрик. Уровни берутся из самого дампа:

- **вход** — лучший ask, «не выше» — ask + `entry_slippage_pct` (0.3%);
- **стоп** — под стеной покупателя, если она ниже входа, иначе под дном дампа, минус
  `stop_buffer_pct` (0.3%); ближе `min_stop_pct` (0.6%) не ставится — выбьет шум;
  дальше `max_stop_pct` (4%) — предупреждение «возьмите позицию меньше»;
- **цели** — откат от дна к максимуму окна на `targets_retrace` (0.382 / 0.618 / 1.0),
  только выше входа; если целей нет — плана нет;
- **прибыль/риск** по каждой цели; ключевая — вторая, ниже `min_rr` → предупреждение;
- **размер** — при `risk_usdt > 0`: монет = риск / (вход − стоп), контрактов = монет / ctVal;
- уровни округляются вниз до `tickSz` инструмента; план актуален `valid_s` (15 мин);
- если цена уже отыграла ≥ 61.8% дампа — предупреждение «вход поздний».

Telegram (HTML, `alerts.sinks` содержит `telegram`):

```
🟢 ПОКУПКА CT · лонг CT-USDT-SWAP
откуп после дампа -3.44% за 2h (с 0.1426 до 0.1365)

Вход: 0.1377 по рынку, не выше 0.1381
Стоп: 0.1355 (-1.6%) — под стеной 0.136
Цели: 0.1388 (+0.8%) · 0.1402 (+1.8%) · 0.1426 (+3.6%)
Прибыль/риск: 0.5 · 1.1 · 2.2
Размер: 4 545 CT ≈ 626 USDT (455 контр.) — на стопе −10 USDT
⏱ актуально до 12:16; ниже 0.1355 идея отменяется

Почему (2/3):
• стена покупателя 0.136 на 51k USDT (6.0× обычного уровня) держится и не снимается
• продавец выдыхается: в конце окна покупки отыграли большую часть продаж

Стакан 20 ур.: покупатели 164k / продавцы 137k USDT
Поток 5 мин: купили 60k / продали 39k (перевес +21k)
SWAP · 29.10 12:01:44 · не финансовая рекомендация, расчёт по уровням
```

Консоль — то же коротко (`Alert.console_text()`). JSONL/вебхук — всё структурой
(`Alert.to_dict()`, план в поле `plan`), чтобы считать статистику попаданий постфактум.

## 10. Риски и как их закрываем

| Риск | Что делаем |
|---|---|
| обрыв WS | backoff до 30 c, полная переподписка, бутстрап свечей перезапрашивается при длинном разрыве |
| потеря целостности стакана | сверка `prevSeqId` с последним `seqId`; при разрыве — переподписка `books` (чистый snapshot), только этого инструмента |
| стоячая стена «протухает» | в инкрементальном режиме свежесть по стакану (`stale_after_s`), а не по `level.ts`: иначе стена выбрасывалась бы ровно на пороге `wall_persist_s` |
| глубина проседает при выедании уровней | храним `store_levels` (100), срез до `levels` (20) только в `summary()` |
| rate limit REST | REST больше не поллится постоянно: только ресинк по требованию, семафор + 429-пауза |
| холодный старт | `state.json` восстанавливает бакеты CVD, ликвидации и кулдаун (атомарная запись, TTL 15 мин) |
| «протухший» стакан | per-level ts, `stale_after_s`, пропуск инструмента |
| ложные срабатывания на тонких альтах | фильтр 1M USDT + top-N по обороту + `min_score` |
| «стена» есть всегда, ratio врёт | лучший бид не считается стеной; база — **среднее** по уровням (медиана у BTC = 16 USDT из-за пыли); стена должна простоять `wall_persist_s` (10 c) |
| трафик `books` на всём рынке (13 ГБ/час) | стакан по требованию: слоты под дампы, TTL, вытеснение слабых (§5.5) |
| «осиротевшая» подписка `books` после реконнекта | `unsubscribe` убирает подписку из списка потока даже без соединения |
| спам алертами | кулдаун на (инструмент, окно) |
| неполные ликвидации | сигнатура только как подтверждение, не как триггер |
| пересчёт «на глаз» | JSONL-лог всех алертов → разбор и тюнинг порогов; в дашборде — история эпизодов с причиной отсева |
| чужая страница управляет сканером через дашборд | только 127.0.0.1 по умолчанию, проверка `Host`/`Origin`, изменения только JSON-запросом, токен из окружения для внешнего адреса |
